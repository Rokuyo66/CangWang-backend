> 2026-09-23 · 對應前端 b61（觀堂角色卡事件泡泡）

## 2. 道緣經濟：多久會碰到門檻

每日來源（每位角色分開算，簽到三人都加）：

| 來源 | 道緣 | 備註 |
|---|---|---|
| 聊天（AI 回覆） | +1／句 | 免費 8 句／日（全角色共用），觀微 12、知己 30、藏往 100 |
| 起卦（歸到該角色） | +3 | 追問 +2 |
| 簽到 | 7 日循環第 3 天 +5、第 7 天 +10 | ≈ +2.1／日，三人都加 |

推算（專注一位角色）：

| 玩家型態 | 每日約 | 到 300 | 到 500 | 到 800 |
|---|---|---|---|---|
| 輕度免費（3 句＋隔天一卦＋簽到） | ~7 | 43 天 | 72 天 | 115 天 |
| 重度免費（8 句＋1 卦 1 追問＋簽到） | ~15 | 20 天 | 34 天 | 54 天 |
| 知己（30 句＋1 卦 1 追問） | ~37 | **8 天** | 14 天 | 22 天 |

結論：
1. **300 → 500 → 800 間距太大。** 輕度玩家頭一個半月除了 c1 什麼都拿不到，恰好是流失最高的時段。要在中間補小節點（§3）。
2. **付費玩家第 8 天就到 300。** 所以開放 STORY_OPEN 那天，c2 必須已經寫好；c3 最晚 +2 週。
3. **老玩家可能已經超過門檻。** 開放前先跑：
   ```sql
   select character_id,
          count(*) filter (where favor >= 300) as ge300,
          count(*) filter (where favor >= 500) as ge500,
          count(*) filter (where favor >= 800) as ge800
     from user_character group by 1;
   ```
   有人 ≥ 某門檻、那一章卻沒內容 → 那一章不准開放，先補內容。

## 3. 節點設計：大節點演劇情，小節點寄一封信

把道緣切成兩種節點。小節點是純文字、成本低，負責填滿大節點之間的空檔；大節點才需要美術與劇本。

### 小節點（每 50：50／100／150／200／250／350／…）— 「他寫了一封信給你」

- 形式：角色口吻的站內信（mail kind=character），夾 **5～20 靈石**。沿用 0063 的 `mail_send`＋`mail_claim`，不必新做 UI。
- 內容：一段只有到了這個熟度他才會說的話，**同時寫入一條額外記憶**（character_memories, source='milestone'）。
  之後聊天時他會引用這段（「上次跟你說過後院那棵樹……」），讓玩家感覺到「他記得」。這就是額外記憶的用途：不是收集品，是會回到對話裡的東西。
- 觸發：後端在道緣跨過節點時寄出（見 §5），不是前端。
- 量：三人 × 每 50 一封，50 到 800 共 16 個點，扣掉 300／500／800 三個大節點 → **每人 13 封，共 39 封文字**。可分批寫：上線只需寫到 250（每人 5 封，共 15 封）。

### 大節點（300 相熟／500 相知／800 知己）— 劇情章

| 獎勵 | 300 相熟 | 500 相知 | 800 知己 |
|---|---|---|---|
| 劇情章 | 第二章 | 第三章 | 第四章 |
| 身分（title） | ✅ | ✅ | ✅ |
| 額外記憶 | 章末那一句 | 同 | 同 |
| 記憶額度 | +1 格（該角色） | +1 格 | +2 格 |
| 靈石 | 30 | 50 | 100 |
| 外觀 | — | 動態頭像框 | 專屬動態頭像＋主題色一套 |

記憶額度加格是「好感換功能」：他能記住你更多事——直接呼應「紀錄手帳本」這個核心。

### 起點（0 初識）— 第一章

三人各一章，**入場選完引路人後就能演**。現在只有大師兄有。師妹、觀貓的第一章是上線必備，不然三人只有一人有故事，跟入場「我們有角色」的承諾對不上。

## 5.1 怎麼填一章（0065 之後）

Supabase → Table Editor → `character_events` → 點一列（或 Insert row）。

| 欄 | 填什麼 | 空白／0 |
|---|---|---|
| id | `角色_c章`，如 `daoshi_f_c1` | 必填 |
| character_id／chapter／seq／title／summary | 誰、第幾章、章名、一句摘要 | 必填（summary 可空） |
| require_favor | 道緣門檻 | 不限 |
| require_cultivation | 修為門檻 | 不限 |
| require_event | 前一章 id | 章首 |
| scenes／choices | 台詞與選項（JSON，照 c1 的格式） | 空的章不能上架 |
| reward_lingshi | 靈石數 | 不發 |
| reward_avatar | 頭像 key（r01～r13；新的要前端 REWARD_AV 先有） | 不發 |
| reward_title | 他的新身分（自動生成可切換的身分，聲口到 character_titles.voice_hint 補） | 不發 |
| reward_memory | 他會記住的一句話 | 不寫 |
| reward_player_title | 玩家稱號（下拉選 player_titles，0066） | 不發 |
| rewards | 其他擴張（JSON），目前只回給前端顯示、不會真的發 | — |
| published | 打勾上架 | 不上架 |

改完即生效，不必出 APK、不必 deploy。

## 5.2 身分與稱號怎麼填（0066 之後）

| | 角色身分（你眼中的他） | 玩家稱號（他眼中的你） |
|---|---|---|
| 表 | `character_titles` | `player_titles`（每角色另寫：`player_title_voices`） |
| 改什麼 | 他自己的立場、語氣 | 他怎麼叫你（`call_as`）、語氣（`voice_hint`） |
| 怎麼拿到 | 了結 `unlock_event` 那章；或事件填 `reward_title` 自動生成 | 事件填 `reward_player_title`；或在 `user_player_titles` 手動加一列 |
| 空白 | `unlock_event` 空＝人人都有 | `call_as` 空＝照舊叫暱稱 |

新增一個角色身分：`character_titles` → Insert row
- `id`：`角色_英文`，如 `daoshi_f_zhangui`（之後別改）
- `character_id`、`label`（顯示的字）、`seq`（排序）
- `voice_hint`：一句，只寫立場／稱謂／在意的事
- `unlock_event`：哪一章了結後解鎖；空白＝預設人人有

⚠ 兩種 `voice_hint` 都**不寫親密程度**。好感分層是安全機制，換身分／稱號不能讓他變熱絡。
改完即生效，不必出 APK、不必 deploy。
