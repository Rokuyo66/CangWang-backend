# 心跡後端 API（待接：前端 repo）

後端這一側已完成並測過（`node dev/xinji-test.mts`，31 條）。這份是給前端的契約。

**這一版取代卦案那一格。** `src/part2.html` 現在是
`case: ()=>toast("卦案尚未開放，敬候觀中通告")`——把它換成開啟**心跡**畫面。
卦案的後端（`case_*` 六支 mode）原封不動留著、照樣能呼叫，只是不再有入口；
要不要在後台留一個測試入口自己決定。

版面參考：設計畫布四張（心事時間軸／單一心事／月誌未持牒／月誌已持牒），
配色與字級直接沿用 `dev/play/shell.html` 的那組變數。

---

## 為什麼是這個形狀（接之前先看，否則會接成一個「卦的清單」）

心跡不是卦曆的另一種排法。差別在**它以「一件事」為單位，不是以「一卦」為單位**。

- 一件事會被問很多次（財運與感情這兩類尤其）。
- 同一件事第二次來問，原本會被一事不二占攔下來說「你問過了」。
  現在只要那一卦帶著 `thread_id`，就不攔——他不是重複問，是就同一件事再問一次。
- 一件事有一條時間線、一條溫度線、一組角色留言、一個應期閉環。

所以前端該畫的是「事」，卦是事底下的條目。畫成卦的清單，這個功能就白做了。

## 成本（決定哪些畫面可以放心地天天開）

心跡預設零 AI。時間軸、溫度線、角色留言、月誌統計全是查詢與純計算，
**唯一會呼叫模型的是月誌卷首語，每人每月一次、走 haiku**。

所以：時間軸與心事詳情可以隨便開、可以下拉刷新、可以進頁就打。
不必像起卦那樣先問「這樣會不會很貴」。

## 十一支 mode

全部走既有的 `interpret` Edge Function，跟站內其他功能同一支 `callInterpret`：
`POST /functions/v1/interpret`，`Authorization: Bearer <JWT>`，body 帶 `mode`。
錯誤一律 200 ＋ `{kind:"err", msg:"…"}`（`msg` 是可以直接顯示給人看的中文）。

| mode | 送 | 回 |
|---|---|---|
| `xinji_timeline` | — | `{threads, notes, quota}` |
| `xinji_thread` | `thread_id` | `{thread, casts, temperature}` |
| `xinji_open` | `title`、`subject?`、`category?`、`cast_id?` | `{thread, quota}` |
| `xinji_attach` | `cast_id`, `thread_id` | `{cast_id, thread_id}` |
| `xinji_close` | `thread_id`, `close`（預設 true） | `{thread_id, status}` |
| `xinji_delete` | `thread_id` | `{thread_id, deleted}` |
| `xinji_suggest` | `question` | `{thread}`（null＝沒有對應的線） |
| `xinji_note_reply` | `note_id` | `{character_id, thread_id, prefill}` |
| `xinji_note_read` | `note_ids[]` | `{read}` |
| `xinji_month` | `ym?`（`YYYY-MM`，預設本月） | 見下 |
| `xinji_month_index` | — | `{months, paid}` |

`profile` 另外多了三個欄位，導覽紅點與額度標示直接讀它，
**不要為了兩個數字在開 App 時多打一支 `xinji_timeline`**：

| 欄位 | 意思 |
| --- | --- |
| `xinjiOpen` | 現在在記幾件事 |
| `xinjiMax` | 這個方案最多記幾件（免費 1／觀微 3／知幾 8／藏往 20） |
| `xinjiUnread` | 未讀的角色留言數（畫紅點用） |

## 時間軸 `xinji_timeline`

開這一支時後端會順手熬一次角色留言（零 AI），所以下拉刷新就會長出新留言。

```js
{
  kind:"ok",
  threads:[{
    id, title, subject, category,
    status,                    // open | closed
    cast_count, opened_at, closed_at, days,
    last_gua, last_digest, last_character,   // 最近一卦：卦名、一句話摘要、誰解的
    due_date,
    due_in,                    // 距應期幾天。**負數＝已過**。null＝這條線沒有應期
    due_answered,              // 已回報過了嗎
    verdict,                   // 1應驗 2部分 3未應 0未發生 null未回報
  }],
  notes:[{ id, thread_id, character_id, kind, body, cast_id, created_at, read_at, replied_at }],
  quota:{ open, max },
}
```

排序後端已經處理好：**在記的在前（依最近有卦），已了結的在後（依結案時間新到舊）**。
前端照陣列順序畫就好，不要自己再排一次。

`notes` 只回**還沒回過**的（`replied_at is null`），最多 12 則。
`kind` 有三種，前端可以用不同語氣的圖示：
`due_passed`（應期到了問你後來呢）／`gone_quiet`（擱著了）／`closed`（結案感言）。

`body` 可能含全形星號包住的動作旁白（`＊觀喵甩了甩尾巴＊`），與閒聊同一套格式，
照閒聊那邊現成的渲染走。也可能含 `\n`。

## 心事詳情 `xinji_thread`

```js
{
  kind:"ok",
  thread:{ id, title, subject, category, status, opened_at, closed_at, cast_count, days },
  casts:[{ id, at, question, gua_ben, gua_bian, digest, character_id,
           due_date, verdict, verdict_note }],   // 由舊到新
  temperature:{
    points:[{ cast_id, at, gua, wang, score, basis }],
    levels:["死","囚","休","相","旺"],           // score 0..4 對應這五等
  },
}
```

**溫度線怎麼畫**：`score` 當縱軸（0 在下、4 在上），`levels[score]` 是那一格的字。
2px 線、只標最低點與最新點，不要每點都標數字。

`basis` 是「這條線在看哪一爻」，**必須顯示出來**（設計稿放在卡片右上）。
它可能是 `妻財`、`妻財（伏神）`、`世爻`、`世爻（此卦未取定用神）`。
不顯示的話，這條線就變成一條沒有依據的折線——那正是這個功能最不該給人的印象。

`points` 的數量**可能少於 `casts`**：算不出旺衰的卦（舊資料 chart 不成形）會跳過，
而不是補一個零。前端不要拿 `casts.length` 當點數。

## 記一件新的事 `xinji_open`

（從閒聊進來的那條路多帶三個欄位，見第四節「先記下這件事」。）

`cast_id` 可省。給了就把那一卦當首卦（從卦曆或剛解完的卦進來的路徑）。

額度滿時回的 `msg` 已經是可以直接顯示的話，免費用戶那一句還會指路到「持玉牒入觀」：

```
心跡同時只記得住一件事。要記新的，得先了結手上那一件——或持玉牒入觀，多幾格。
```

不要自己另寫一句「已達上限」蓋掉它。

## 就這件事再問一卦

**這是心跡最重要的一條接線，而它不在上面十一支裡。**

起卦時（既有的起卦 API）body 多帶一個 `thread_id`：

```jsonc
{ "mode": "cast", "question": "…", "lines": [...], "thread_id": "<心事 id>" }
```

帶了之後：

1. **不吃一事不二占的攔截**。他不是重複問，是就同一件事再問一次。
2. 這一卦自動掛到那條線上，時間軸與溫度線立刻更新。

帶一個不存在、不是他的、或已了結的 `thread_id`，後端當作沒帶（照常攔截），
不會回錯——所以不必先驗。

起卦**之前**可以先打 `xinji_suggest` 帶問句，回到一條線就把畫面從
「你問過了」換成「這件事我記得，現在到哪了？」——牆翻成線的那一下，就在這裡。

## 回牠一句 `xinji_note_reply`

回 `{character_id, thread_id, prefill}`。前端該做的是：

1. 開啟與 `character_id` 的閒聊。
2. 把 `prefill`（例如 `關於「阿凱這條線」——`）填進**輸入框**，游標放在後面。

**不要代發。** 代發的話那句話就不是他說的了，而閒聊的價值正好在那裡。
計費照閒聊既有規則走（額度內免費、超出每則扣靈石），這一支本身不計費。

## 月誌 `xinji_month`

```js
{
  kind:"ok",
  ym:"2026-03", current:true,        // current＝這是當月（尚未終月）
  stats:{
    casts, by_category:{感情:5, 財:4, …},
    due_total, answered,
    verdicts:{ hit, partial, miss },
    busiest:{ date, casts } | null,
    open_longest:{ id, title, days, casts } | null,
    closed,
  },
  threads:[{ title, casts }],        // 這月動過的心事
  preface: "…" | null,               // 卷首語。只有持牒者才有
  locked: true | false,
  locked_reason: "三月的卷宗已經齊了。只是觀中無人為你翻開。",   // 只在 locked 時有
  empty: true,                       // 這月沒卦（付費者也不生成）
  gen_failed: true,                  // 生成失敗，統計照給
}
```

**`stats` 免費用戶也拿得到，這是刻意的。** 那本來就是他自己的資料，鎖它只顯得小氣，
而且鎖了他就不知道卷宗裡有東西。封的是「有人為你翻閱」那一層（`preface`）。
設計稿上半截那三個數字（卦／記掛／已回報）就是 `stats`，未持牒也照畫。

`locked` 時把 `locked_reason` 印在封緘卡上，底下才是「持玉牒入觀」的鈕。

`gen_failed` 或 `empty` 時 `preface` 是 null，但 `locked` 是 false——
這時**不要**顯示付費牆，就照常畫統計。付了錢還被推銷是最傷的體驗。

## 往月 `xinji_month_index`

`{months:[{ym, casts, opened}], paid}`，新到舊。`opened` 是「這一卷已經生成過卷首語」。
未持牒者一律畫成「未啟封」——訂了之後回頭補看往月，是續訂的理由。

## 先只上 APK，不上網頁

心跡這一版**只在 App 裡開，網頁版維持看不到**。

照藏經那一套走（見 `B26-UNPUSHED.md`）：那一格的入口先寫成 `hidden`，
由 `part2` 依 `isNative` 把 `hidden` 拿掉。網頁版不拿，那一格就不存在。

```html
<button id="xinjiTab" hidden>心跡</button>
```

**不要用 CSS 藏。** `display:none` 的東西在 devtools 裡點得開，而心跡背後那幾支
API 是真的會回資料的——藏得不乾淨等於網頁版也上了，只是難按到。

後端這側不必配合做任何事：那十幾支 mode 在網頁帶 JWT 進來時一樣會回答。
真正的閘門是「網頁上沒有那個入口」，不是後端擋。這個取捨要知道：
**它擋的是誤觸，不是刻意繞過的人。** 心跡沒有任何不能給那個帳號本人看的東西
（全都是他自己的卦），所以這個強度夠用；哪天有真的要擋的東西，得另外做。

## 前端要做的事

1. `src/part2.html` 那行 toast 換成開啟心跡畫面，那一格改名「心跡」，並照上面加 `hidden`。
2. 心跡四頁：時間軸（心事／月誌／語音三個分頁）、單一心事、月誌、語音收藏。
3. 起卦流程接兩個點：送出前 `xinji_suggest`，起卦時帶 `thread_id`。
4. 卦曆的每一卦加一顆「記成一件事／歸到某條線」（`xinji_open` / `xinji_attach`）。
5. 導覽紅點讀 `profile.xinjiUnread`。
6. `appBuild` +1 再出 APK。

# 二、語音收藏

## 為什麼要做

朗讀是伺服器合成的（MiniMax，`_shared/tts.ts`）。**收藏＝把已經合成好的音檔留下來**，
之後重聽不再呼叫 TTS——所以語音頁播放幾百次都是零邊際成本，
而它同時是留存（想再聽一次師兄那句話）與訂閱誘因。

格數：免費 3 段、觀微 10、知幾 30、藏往 100。

## 上傳那一套已經拿掉了（2026-08 改版）

舊契約要前端把 mp3 PUT 到私有的 `voice` bucket，再回頭 `voice_confirm`。
那個設計做不出來，也不該做：

- **前端手上根本沒有那個 mp3。** `reading-tts.js` 拿到的是 `tts` bucket 的
  公開網址，它從頭到尾沒有握過檔案——所以「收藏語音」那顆鈕一直沒被做出來，
  而心跡語音頁的空狀態卻寫著要人去按它。
- **音檔本來就永久留著了。** `tts` bucket 的鍵是 `sha256(模型|聲線|逐字文本)`、
  `cacheControl` 一年。再複製一份到另一個桶，是為同一段聲音付兩份儲存費。

現在一則收藏是**一個指標清單**：哪幾個音檔、照什麼順序播。
`voice_save`／`voice_confirm` 兩支已刪，換成一支 `voice_keep`。
`voice` bucket 不再需要（留著沒刪，它是空的）。

## 三支 mode

| mode | 送 | 回 |
|---|---|---|
| `voice_list` | — | `{clips, quota, tts_quota}` |
| `voice_keep` | `cast_id`＋`part`，**或** `chat_id` | `{clip, duplicate, quota, tts_quota}` |
| `voice_delete` | `clip_id` | `{id, deleted}` |

## 收藏一段

```js
await apiInterpret({ mode: "voice_keep", cast_id: castId, part: "body" });
// part："body"＝批文本體；數字＝第幾則追問。與 mode:"tts" 同一套形狀。

await apiInterpret({ mode: "voice_keep", chat_id: msgId });   // 閒聊裡角色說的那一句
```

收藏走的是**與朗讀完全相同的合成路徑**（伺服器內部就是呼叫 `speakCast`）：

- 已經聽過 → 命中快取 → 不花錢、不吃朗讀額度。
- 沒聽過就按收藏 → 合成一次 → 與按下朗讀同一個價錢、同一份額度。

不另立一條規則。兩條路遲早會走偏，而走偏的那天沒有人會發現。

回應：

```json
{ "kind": "ok",
  "clip": { "id": "…", "title": "《水天需》", "subtitle": "那筆尾款收得回來嗎",
            "character_id": "daoshi_m", "duration_ms": 93334,
            "peaks": [46, 72, 31, 88, …],
            "parts": [ { "url": "https://…/a.mp3", "narrator": false, "ms": 66667,
                         "text": "所問：那筆尾款收得回來嗎。水天需，需者須也…" },
                       { "url": "https://…/b.mp3", "narrator": true, "ms": 26667,
                         "text": "他把茶盞挪開，指節在案上輕輕敲了兩下。" } ] },
  "duplicate": false,
  "quota": { "used": 1, "max": 3, "can_add": true },
  "tts_quota": { "used": 420, "max": 5000, "left": 4580, "left_readings": 3,
                 "day_used": 420, "day_max": 3000 } }
```

`duplicate: true`＝這一段已經在收藏裡了。**那不是錯誤**，畫面上說「已經在心跡的語音裡了」即可。

## 閒聊也念得了（2026-08 加）

`mode:"tts"` 與 `voice_keep` 都多認一個 `chat_id`——那是 `chat_messages.id`。
**這個 id 以前沒下發過**，現在兩處都給：

- `mode:"chat"` 的回應多一個 `msg_id`（這一則回覆的 id）
- `mode:"chat_history"` 的每一則多一個 `id`
  （順帶把排序改成依 `id`：同一問答常常同一個 timestamp，
  以前得再補一個 role 鍵去猜誰先誰後，而 `id` 是 bigserial，一個鍵就夠準）

```js
await apiInterpret({ mode: "tts", chat_id: msgId });        // 念這一句
await apiInterpret({ mode: "voice_keep", chat_id: msgId }); // 收下這一句
```

**只念得了角色說的（`role='assistant'`）。** 念使用者自己打的字沒有意義，
卻等於開了一個「你給我文字我念給你聽」的入口——那正是「客戶端只送 id、
不送文字」這條鐵則要擋的東西（見 `_shared/tts.ts` 檔頭）。送使用者那一則會回
「只念得了角色說的話」。

為什麼閒聊該有聲音：師兄的聲線在解卦那裡有、在閒聊裡沒有，等於同一個人在兩個
地方是兩種存在。而閒聊才是人真正停留的地方——卦問完就結束，話會一直講下去。

一句閒聊約一兩百字，比一篇批文（抓 1,300 字）便宜一個量級；`＊…＊` 的旁白照樣
換旁白那把嗓子，與批文同一套分軌。**額度、快取、去重完全共用**：同一段字在
兩邊都只合成一次、只收成一則。

收下來的 clip 形狀與批文那邊完全一樣（所以語音頁與 `voice-player.js` 一個字
都不必改），差別只在三欄：

| 欄位 | 批文 | 閒聊 |
|---|---|---|
| `cast_id` | 那一卦 | `null` |
| `message_id` | `null` | 那一句 `chat_messages.id` |
| `kind` | `reading`／`followup` | `chat` |
| `title` | `《水天需》` | `大師兄・閒聊` |
| `subtitle` | 當初問的那句話 | **他當時說了什麼**（緊鄰在前的那一則使用者發言） |

**格數不分來源共用一份**（免費 3 段、觀微 10、知幾 30、藏往 100）——
語音收藏是一個架子，不是兩個。對話清掉時 `message_id` 設為 `null`，
收藏不受影響（「收藏過的永遠能聽」對兩種來源同樣成立）。

## 清單 `voice_list`

`clips` 依 `created_at` 新→舊，最多 120 則。每一則的 `parts` 照播放順序，
**要一段接一段播完才算一則播完**（長批文在伺服器切過段，角色台詞與旁白還會換嗓子）。
網址是公開且永久的，不必擔心過期。

一則收藏的欄位，以及它是給畫面上的哪一件事用的：

| 欄位 | 是什麼 | 畫面上用在哪 |
|---|---|---|
| `title`／`subtitle` | 卦名／當初問的那句話 | 卡片那兩行。**不要自己組**——組出來的字會跟伺服器的版本走偏 |
| `duration_ms` | 整則多長（毫秒） | 收起來時顯示的「2:14」；展開後是進度條的全長 |
| `parts[].url` | 音檔（`tts` bucket，公開永久） | `<audio>` 的 src，照順序播 |
| `parts[].text` | **這一段念的字** | 點下去攤開的逐字稿，念到哪一段哪一段是墨色 |
| `parts[].narrator` | 這一段是不是旁白（另一把嗓子） | 逐字稿裡旁白那幾段縮排偏淡 |
| `parts[].ms` | 這一段大約多長 | 跨段的進度與「還剩幾秒」 |
| `peaks` | 一串 0..100 的高度 | 波形那一排柱子 |

`parts[].text` 為什麼要由伺服器帶：**客戶端手上沒有原文**。它送出去的只有
`cast_id`，念什麼一律伺服器自己去 `casts` 撈（見 `_shared/tts.ts` 的檔頭：
開放送文字等於把金鑰做成公用 TTS）。所以要在畫面上把念的字攤開來，
只有這一條路。

`duration_ms` 與 `parts[].ms` 都是**估的**（字數 ÷ 每秒 4.5 字）。真值要下載
整個 mp3 解檔頭才知道，為了清單上一個「2:14」去下載幾 MB 不划算。
播放時 `<audio>` 一載到 metadata 就有真的 `duration`，那時換成真值即可——
先估後換，人不會在按下播放之前看到一片空白。全長是各段之和，不是總字數
換算一次：兩邊各算各的，播到最後一段就會「條滿了、秒數還剩兩秒」。

`peaks` 是**畫的，不是量的**：由該則的內容指紋展開成一串固定的高度。
真波形要把整個 mp3 抓下來解碼；純亂數則會讓同一則每次打開都長不一樣，
看起來像壞掉。由指紋展開＝每則各有各的樣子、每次都一樣，成本是零。
**它不代表音量，不要標成音量。** 想要真的跟著聲音跳，前端疊一層 WebAudio
的 analyser 就好，這串保底的形狀不必動。

**0047 之前收的那幾則沒有 `text`。** 字沒有不見——快取鍵就是由原文算的，
所以開這一頁時伺服器會順手把它算回來（一次補幾則，補完寫回去，自己會補完）。
對不上的（那一卦已經刪了、或切段的參數調過）`text` 會是 `null`：
那一則照樣聽得完，只是展不開全文。畫面上說一句就好，不要留一塊空白——
空白會被當成又壞了。

## 播放器：一顆鈕要一次做四件事

先前那一版只做了「開始放聲音」，於是按下去之後畫面上什麼都沒變：icon 還是
三角形、字沒有攤開、沒有進度、不知道還剩多久。聲音在響，但畫面看起來像壞掉——
人只能盯著一顆沒有反應的圓圈猜它到底有沒有在動。所以按下播放要同時：

1. **icon 換成暫停**，`aria-label` 一起換（只換圖不換 label，讀螢幕的人會一直聽到「播放」）。
2. **把 `parts[].text` 攤開**，念到哪一段哪一段是墨色，念過的退成次要色；
   `narrator` 那幾段縮排偏淡（聽的時候本來就分得出來，看的時候也要）。
3. **波形填成進度**，整條可按、按哪裡跳哪裡。
4. **右邊說「剩 1:19」**，不是只說總長——人想知道的是還要多久，不是這段有多長。

另外三條，少了哪一條都會出事：

- **整頁只有一個 `<audio>`。** 一張卡一個的話，連按兩張就是兩段聲音一起響，
  而且第一張的 icon 永遠回不到播放鍵（沒有人會去通知它）。
- **進度以「整則」為單位算**，不是這一個音檔。否則播到第二段時進度條會跳回開頭。
- **展開與播放是兩件事。** 按播放順便展開；但收起來不該把聲音停掉，
  收起來的卡上 icon 仍是暫停——混在一起就會出現「收起來之後停不掉」。

`dev/web/voice-player.js` 是照這份契約寫好、可以直接用的一支模組
（複製到前端 repo 的 `src/modules/`，`mountVoicePlayer(root, payload)`，
回傳的 `stop()` 在離開這一頁時呼叫）。它是一支獨立的 ES module、沒有依賴，
色票走心跡那一套 CSS 變數，宿主要換皮直接蓋。跨段接續、跳段、真長度換估長度、
音檔掛掉時把鈕放回去，都在裡面了。頭像目前取卦名第一個字當備援，
正式接的時候換成 `character_id` 對應的立繪。

## 額度的兩個承諾（心跡不能全是付費產物）

1. **收藏過的永遠能聽。** 免費、無限次、朗讀額度用完了也能聽、玉牒到期了也還在。
2. **格數擋的是「再收新的」，不是「保留」與「重聽」。**
   藏往收了 100 段之後掉回無牒，那 100 段一段都不會消失，也不會被藏起來。
   所以 `quota.used` **可能大於 `quota.max`**（顯示成「10 / 3」即可，不必特別處理），
   `can_add` 才是「現在還能不能收」。

丟一則收藏**不刪音檔**——那個檔在 `tts` bucket 是全站共用的快取，
別的收藏、別人的重聽都可能指著它。

## 朗讀額度 `tts_quota`

以**月**為單位、依玉牒分階，下個月一號重新計算（不滾存）：

| 階 | 月字數 | ≈幾則批文 |
|---|---|---|
| 無牒 | 5,000 | ~3 |
| 觀微 | 12,000 | ~9 |
| 知幾 | 30,000 | ~23 |
| 藏往 | 60,000 | ~46 |

一則批文抓 1,300 字（`CHARS_PER_READING`）。

`day_max` 是日煞車（月額度的四分之一，下限 3,000），不是額度——正常人碰不到，
它擋的是跑掉的迴圈在一個下午燒完整個月。

**命中快取不吃額度**：重聽、收藏聽過的段落都是零消耗。

畫面上請用「還能請人念約幾段」來講，不要講字數——沒有人知道 1,580 個字是多少東西。
**換算由伺服器做**，直接用 `tts_quota.left_readings`；前端不要自己除，
兩邊各除一次就會出現「這裡說 3 段、那裡說 2 段」。

`speakCast` 的額度是**整篇一次檢查**，不是一段一段扣。額度不夠時
一個字都不會送去合成——一段一段扣的話，長批文會在中間某一段用完額度，
前幾段已經付錢，而使用者一個字也沒聽到。

`mode:"tts"` 的回應也夾帶同一份 `tts_quota`。

## 朗讀那一排要加的鈕

`readToolsHtml()` 從兩顆變三顆：朗讀解析／**收藏語音**／存成圖片。
追問底下那一排（`threadTtsHtml`）同樣加一顆「收藏」。
窄螢幕上第三顆會換行，這是可以接受的——縮字級把三顆硬塞成一列，每顆都會小到不好按。

**閒聊那邊**：角色的每一個對話框長按（或右側小鈕）出兩個動作——「念給我聽」與
「收下這句」，送的都是那一則的 `chat_id`。不要做成常駐的兩顆鈕：閒聊是一長串
對話框，每一格都掛兩顆鈕會把畫面吵成一片按鈕海，而人只會想聽其中一兩句。


# 三、貼紙

## 為什麼要做

零 AI、純毛利，和配色同一類但比配色好賣：配色一個帳號只買一次，
貼紙是包、可以一直出新的，而且**人是在「想貼」的那一刻掏錢**，
不是在商店頁被推銷的時候。所以價錢寫在抽屜裡，不另跳商店頁。

開場四包：觀中常備（免費 8 張）、觀喵の日常（免費 4 張）、
節氣・二十四（160 靈石）、硃砂印記（120 靈石）。
**免費包不必買、也不會寫進 `owned_packs`**——它一律視同已有。

## 六支 mode

| mode | 送 | 回 |
|---|---|---|
| `sticker_shelf` | — | `{packs, max_per_surface}` |
| `sticker_buy` | `pack_id` | `{pack_id, name, paid}` |
| `sticker_place` | 見下 | `{sticker, count, max}` |
| `sticker_move` | `id` ＋要改的欄位 | `{sticker}` |
| `sticker_remove` | `id` | `{id, removed}` |
| `sticker_layout` | `surface` | `{surface, stickers}` |

`packs` 已擁有的排前面，未購的直接帶 `price`。下架的包完全不出現。
每一包都帶 `stickers:[{id, name, asset}]`——未購包的也帶，畫成鎖著的縮圖。
`asset` 是前端資產鍵（`assets/stickers/<asset>.svg`），圖不在後端。

## 貼在哪一頁

`surface` 只認四種形狀，其餘一律回錯：

```
timeline            心事總覽
voice               語音收藏頁
thread:<uuid>       某一條心事
month:YYYY-MM       某一個月的月誌
```

**心跡三頁的回應已經夾帶那一頁的貼紙**（`payload.stickers`），
不要為了貼紙多打一支 `sticker_layout`——那支是給不走那三支的頁面用的。

## 座標：錨點 ＋ 偏移

這是唯一需要想清楚的地方，接錯了貼紙就會亂跑。

| `anchor` | `anchor_id` | `x` | `y` |
|---|---|---|---|
| `page` | null | 寬度的 **0..1** | 距內容頂端的 **px** |
| `thread` / `cast` / `note` | 那張卡的 id | 距該元素左上角的 **px，可為負** | 同左 |

為什麼不全用相對座標：內容一長（時間軸新增一件心事），貼紙就跟它原本貼著的
那張卡錯開了，而人貼的時候心裡想的是「貼在那筆尾款上」。
錨在卡片上的貼紙會跟著卡片走——卡片移動、排序改變、內容變長都不會跑掉。

負偏移是刻意允許的：設計稿裡那枚壓在卡片右上角、露出一半的銅錢就是 `x:-18, y:-14`。

其餘欄位：`rot` 度數（−180..180）、`scale`（0.4..3）、`z`（後端管，新貼的一定最上層）。
`sticker_move` 帶 `front: true` 可以把一張提到最上層。

一頁上限 24 張，滿了回的 `msg` 是「這一頁已經貼了 24 張，再貼就看不見字了。撕一張再貼。」

# 四、閒聊 → 心跡 → 起卦（2026-08 加）

## 為什麼要接這一段

心跡沒人用，原因不在心跡本身，在**入口**：要用它，得自己想到去開那一頁、
自己想一個標題、自己把事情再打一遍。沒有人會為了「被記著」做這三件事。

而**話剛講完、問句剛理好的那一刻，是唯一不必重打一遍的時刻**——事情都在上面，
角色也剛把它收攏成一句。所以順序是：

```
閒聊 → 角色擬題（[[DRAFT]]） → 「先記下這件事」 → 起卦（帶著 thread_id）
                                     ↑ 新的這一段
```

反過來（先起卦、事後才問要不要記）行不通：那一刻他只想讀卦，
把行政動作插在那裡，十個有九個會關掉。

而且這一段**接上去之後，一事不二占就不再是牆**：同一件事第二次來問，
只要那一卦帶著 `thread_id` 就不攔——他不是重複問，是就同一件事再問一次。
這條線是心跡整個功能的立足點，現在它才真的有人走得到。

## `chat` 多回一個 `xinji`

**零 AI、只在真的擬出題的那一刻算**（兩次查詢）。純閒聊、探詢輪一律是 `null`——
每一則都問「要不要記下來」，正是心跡最不該有的樣子。

```json
{ "kind":"ok", "reply":"…", "draft":"三個月內那筆尾款收得回來嗎？", "draftYong":null,
  "xinji": {
    "thread":  null,
    "propose": { "title":"那筆尾款", "gist":"尾款拖了兩個月，對方一直說再等等，他不敢催。" },
    "open": 0, "max": 1, "can_add": true,
    "fallback": null } }
```

| 欄位 | 意思 | 畫面上該長什麼樣 |
|---|---|---|
| `thread` | 這件事**已經在記了**（`{id, title, casts}`） | 「這件事你在記了：那筆尾款（問過 2 次）」→ 起卦直接帶這個 `thread_id`，不必再問 |
| `propose` | 沒對上時替他預備好的一條線 | 「先記下這件事：〔那筆尾款〕」，**標題與那句總結都要讓他改得動** |
| `open`／`max`／`can_add` | 在記幾件／最多幾件／現在還記不記得下 | `can_add:false` 時不要出一顆按了會失敗的鈕 |
| `fallback` | 記不下新的時，指出的一條現成的線 | 「記不下新的了。要不要就記在『那筆尾款』底下？」 |

`thread` 認的是**與一事不二占同一個鍵**（`question_norm`），對不上時再比一次事由
與現有線的標題／標的是否互相包含（「阿凱」對上「阿凱這條線」）。兩層都對不上就是
新的一件事——寧可多開一條也不要歸錯：歸錯的那條線，溫度曲線與應期閉環從此都是
別件事的。

`propose.title`／`gist` 從哪來：角色擬題時順手給的。標記多了兩格
（`[[DRAFT|問句|用神|事由|一句話]]`），**兩格都可以不給**——舊稿與免費層常漏，
漏了不影響擬題本身，標題退回由問句切出來的粗略版（`topicOf`），總結就是 `null`。
硬湊一個名字比空著更糟，何況名字他自己會改。

## 「先記下這件事」＝ `xinji_open` 多帶三個欄位

```js
const { thread } = await apiInterpret({
  mode: "xinji_open",
  title:    editedTitle,        // 使用者可能改過的
  question: draft,              // ★ 擬好的那一句
  note:     editedGist,         // 一句話總結，落成這條線的第一則留言
  character_id: characterId,    // 誰陪他聊到這裡的（留言要有人說）
});
// 接著才起卦，帶上 thread_id
await apiInterpret({ mode: "cast", question: draft, thread_id: thread.id, /* … */ });
```

- **`question` 一定要帶。** 從閒聊開的線還沒有卦，`question_norm` 只能由它頂上；
  不帶的話，他下一步真的去起卦會被一事不二占擋在門外——而他前一步才剛把這件事
  記進心跡。那是整條路上最傷的一種擋法。
- `note` 落成 `thread_notes` 的一則（`kind:"from_chat"`），一條線只落一次。
  **不要塞進 `title`**：title 是這件事的名字（要短、時間軸上一眼掃過），
  總結是內容；混在一起，時間軸就變成一列長句子。
- 沒帶 `character_id` 就不留言，但線照樣開得起來（留言必須有人說）。
- 那條線的 `category` 在開的時候是空的（還沒有卦）。**第一卦落下時後端自動補上**，
  已經有分類的不覆蓋——時間軸的分類色與月誌的分類統計都吃這一欄。

## 前端已經接好了（CangWang-web · `claude/voice-playback-feature-p9ebt8`）

上面這一整節與第二節的語音，前端那一側已經照這份契約接完並在 Chromium 上實跑過：

| 東西 | 落在哪 |
|---|---|
| 播放器（那四件事） | `src/modules/voice-player.js`＋`src/styles/voice.css`，`voiceMount(root, clips, opts)` |
| 收藏清單 | **道籍›語音**（`renderVoiceTab`）——心跡那一頁還沒進 web repo，而按了收藏總不能是丟進一個看不見的抽屜。心跡接上之後把這一支整支搬過去即可，`voiceMount` 不在乎自己掛在哪 |
| 閒聊念／收 | 角色的泡泡**點一下**才長出兩顆鈕（不常駐，理由見上面「朗讀那一排要加的鈕」）；念走 `ttsSpeakChat`（`reading-tts.js`），送的是 `chat_id` |
| 批文那排第三顆 | `readToolsHtml` 的「收藏語音」，追問那排也補了一顆 |
| 擬題卡的心跡段 | `showDraftCard(who, q, yong, raw, xinji)`，三種狀態都畫了；記下之後 `qMeta.threadId` 一路帶到起卦的 `thread_id` |

**心跡本體（時間軸／單一心事／月誌／貼紙）還不在 web repo 的 main 上。**
這份契約寫的十一支 mode 前端一支都還沒接——語音與擬題那條路能先接，是因為
它們掛在既有的畫面上（道籍、閒聊、批文），不必等心跡那一頁。

## 這一段刻意沒有的東西

**不自動建立心事。** `xinji` 只是把東西備好放在那裡，按不按是他的事。
自動建的話，每一次隨口問問都變成一件「被記掛的事」，而免費只記得住一件——
第二天他想記真正在意的那件時，額度已經被一句隨口的問話佔掉了。

**不替他改標題。** `propose.title` 是預設值不是決定，前端一定要讓他改得動。

**沒有多花一次模型呼叫。** 事由與總結是擬題那一次順手多吐兩格，
心跡這邊的比對與額度全是查詢與字串比對。這一整段的邊際成本是零。

## 這一版刻意沒有的東西

**沒有自動建立心事。** 起卦不會自己長出一條線——那會讓每一次隨手一問都變成
一件「被記掛的事」，而多數卦本來就是問完就算了。記不記，是他自己決定的動作。

**沒有心事的排序／標籤／搜尋。** 免費 1 條、最高 20 條，還不需要。

**沒有把統計存成快照。** 月誌的統計一律現算，因為回評會遲到（三月的卦，人四月才回報）。
所以同一個月份反覆打，數字**可能會變**——那是對的，不是 bug，不要快取它。

**沒有真的波形，也沒有真的長度。** 兩者都要把整個 mp3 抓下來解碼，
而清單上一則要顯示一個秒數、一排柱子——為了這個下載幾十 MB 不划算。
長度用字數估、播放時換成 `<audio>` 量到的真值；柱子由內容指紋展開。
`peaks` 不是振幅，別把它接到任何「音量」的說法上。

**沒有逐字對時間。** 逐字稿是以「段」為單位跟著跑的（一段＝一個音檔），
不是逐字高亮。逐字要 TTS 回時間戳，MiniMax 這條路上沒有，硬估會飄，
飄掉的高亮比不高亮更煩人。

**貼紙沒有自由縮放以外的變形**（不能翻轉、不能裁切、不能改色），
